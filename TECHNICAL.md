# TECHNICAL.md — System Architecture & Engineering Decisions

## System Architecture

```
User message (HTTP POST /api/chat/)
        │
        ▼
┌─────────────────────────────────────────────────────┐
│  ChatEngine.respond()                               │
│                                                     │
│  1. QueryRouter          → intent classification    │
│     (keyword matching, no LLM)                      │
│                                                     │
│  2. TradeoffParser       → structured ParsedIntent  │
│     (LLM call, temp=0)  → fallback: regex           │
│                                                     │
│  3. _retrieve()          → FAISS vector search      │
│     + Python filters     → price/size/color applied │
│                                                     │
│  4. CheckoutStateMachine → cart state transition    │
│     (pure Python)        → may short-circuit LLM    │
│                                                     │
│  5. PromptBuilder        → context + tradeoff hint  │
│                                                     │
│  6. OllamaClient         → Llama 3 (local)          │
│     generate()           → stream=True, 2 retries   │
│                                                     │
│  7. HallucinationGuard   → post-generation check    │
│     validate()           → fallback if flagged      │
└─────────────────────────────────────────────────────┘
        │
        ▼
JSON response: answer, cart, tradeoff, filters_applied
```

**Stack:**
- **Django 4.x** — HTTP layer, ORM, session management via `Conversation.session_id` (UUID)
- **FAISS** — dual flat-index over product embeddings and support doc embeddings; retrieved at k=5 and k=3 respectively
- **Llama 3 (7B via Ollama)** — runs locally; accessed via `http://localhost:11434/api/chat` with `stream=True` to keep the socket alive through long generation
- **PostgreSQL / SQLite** — `Conversation` and `Message` models; `Conversation.metadata` is a JSONField used for cart state

## The AI / Deterministic Boundary

This is the most deliberate design decision in the codebase. The boundary was drawn at the point where correctness matters more than flexibility.

**LLM handles:**
- Natural language understanding — "something cozy for winter evenings under 40 bucks" → structured intent
- Generating product recommendations with explanations, including tradeoff reasoning
- Answering support queries (returns, shipping, policies) from retrieved doc context
- Conversational continuity — remembering earlier parts of the chat via injected history

**Python handles:**
- Price/size/color filtering (in `_retrieve()`) — filtering is exact. The LLM cannot be trusted to reliably exclude a $75 product when the user said "under $60." One hallucinated price in a recommendation destroys trust. Python does `if p["price"] <= max_price` and that's it.
- Cart state transitions — the state machine (`BROWSING → AWAITING_CONFIRM → CONFIRMED → CHECKOUT_COMPLETE`) runs on keyword triggers. The LLM has no memory between API calls; asking it to "remember" what's in the cart across turns would require including the full cart in every prompt (extra tokens) and still risks it mis-stating the cart contents. A Python dict is $0.00 per operation and never hallucinates.
- Checkout confirmation step — the one-question confirm gate (`"Add X for $Y? (yes/no)"`) is generated by the state machine, not the LLM. This keeps the critical "was this intentional?" gate under deterministic control.
- Hallucination remediation — if the LLM's answer contains an unverifiable price or suspicious product name, the `HallucinationGuard` replaces the entire response with a Python-built fallback. The replacement never touches the LLM.

The guiding principle: **use the LLM for things that require language understanding; use Python for things that require correctness.**

## Failure Handling

### Scenario 1: Ollama is down (connect error or timeout)

`OllamaClient.generate()` raises a `requests.exceptions.ConnectionError` or `requests.exceptions.Timeout`. The flow:

1. `TradeoffParser.parse()` catches the exception in its `try/except`, logs a warning, and immediately calls `_keyword_fallback()`.
2. `_keyword_fallback()` extracts price bounds, tradeoff signals, colors, and sizes from the raw query using regex. Returns a valid `ParsedIntent` with no LLM involvement.
3. `ChatEngine.respond()` propagates the exception from `self.llm.generate()`. This is caught by the view's top-level handler and returns a 503 with a user-facing message: "Our AI assistant is temporarily unavailable. Please try again in a moment."
4. The `CheckoutStateMachine` still runs. Cart operations (confirm, checkout, clear) work normally even with Ollama down — they never call the LLM.

### Scenario 2: LLM returns malformed JSON (TradeoffParser)

The `_parse_json()` method:
- Strips markdown code fences (` ```json ``` `) the model sometimes adds despite instructions
- Extracts the first `{...}` block with a regex search, guarding against preamble text
- Calls `json.loads()` inside a `try/except json.JSONDecodeError`
- Validates each field type defensively (e.g., `_safe_float()` for price values)

If any of these steps raises, the exception propagates to `parse()`, which catches it and calls `_keyword_fallback()`. The user never sees a 500.

### Scenario 3: LLM hallucinates a product name or price

`HallucinationGuard.validate()` runs after `llm.generate()` for product-intent turns:

**Price check:** Every `$X.XX` pattern in the answer is extracted. Each value is checked against the set of known prices from `retrieval.products` with a ±$0.50 tolerance (handles rounding). One unverifiable price → immediate discard.

**Name check:** Applied when the answer appears to reference products (contains `$`, "product", "item", "model"). Capitalised n-grams (2–3 words) in the answer are matched against known product names via word-overlap ratio. If a proper-noun-like phrase doesn't map to any retrieved product, it's flagged.

**Fallback:** `_build_fallback()` constructs a response directly from the Python product list — name, price, and a truncated description. Format is deterministic and tested. The LLM is not called again. The hallucination event is counted in `conversation.metadata["hallucination_count"]` for session-level observability.

**Guard is skipped when:**
- `retrieval.products` is empty (no ground truth to check against)
- `intent` is `"support"` (support answers don't reference product names/prices)

## Known Limitations

- **Hallucination guard uses surface-level heuristics.** The name check relies on capitalisation patterns and word overlap, not semantic similarity. A model that paraphrases a product name ("waterproof hiking boots" for a product named "Trail Defender Pro") would pass the check. A proper implementation would embed both the answer and the product names and check cosine similarity.

- **FAISS index is static.** The index is built once at startup. Adding a new product requires a full re-index. For a production system, the index would be rebuilt incrementally on product updates or swapped via a background job with no downtime.

- **Session state is not durable across server restarts.** `Conversation.metadata` is persisted to the DB, but the in-memory `ChatEngine` singleton does not cache conversation state — it's re-fetched from the DB on each request. This is correct behaviour, but the FAISS index (loaded into RAM) will need to be rebuilt if the server restarts.

- **TradeoffParser makes a second LLM call per user message.** For the hackathon, this is acceptable — it's a low-token call (temp=0, structured JSON). In production, this should be merged into the main generation call using a structured output API (e.g., Ollama's `format: "json"` param) to halve the round-trip count.

- **Cart has no quantity support.** Each "add" appends one instance of a product. Quantity tracking would require a `{sku, quantity, price}` structure and a modify-quantity state in the machine.

- **`last_products` is passed from the retrieval result at the time of the "add" trigger.** If the user browses across multiple turns without specifying a product, the state machine picks the first result from the most recent retrieval. An explicit "I want the second one" disambiguation flow is not implemented.
